# Match key lives in a sidecar file, not inside request YAML files

The original plan stored the match key (`operationId`) as an extra field directly in each generated request YAML file. Inspecting the actual `@opencollection/types` schema and a real Bruno-generated collection during implementation showed request files have a closed set of fields with no per-item extensions point, and Bruno's own internal object-model validation (`@usebruno/schema`) is strict `noUnknown`. There's no way to confirm the Bruno app preserves an unrecognized field through an open-and-save round trip, and every available signal suggests it might not. Rather than risk silently losing match-key tracking the first time a user opens a synced collection in the actual app, sync state (`operationId → file path`) is kept in `.bruno-openapi-sync/state.yml`, a sidecar this tool owns exclusively that Bruno never reads or writes. The cost: losing that sidecar loses sync state entirely, with no fuzzy-rebuild fallback (consistent with the no-fuzzy-adoption rule) — but that's a safer failure mode than silent, undetectable corruption of match keys embedded in files the app itself manages.
